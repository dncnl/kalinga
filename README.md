# Kalinga — Developer Onboarding

Welcome to **Kalinga**, an AI care companion for migrant caregivers. This guide gets a new developer from a fresh clone to a running local environment, and covers the rules everyone on the team follows. Read the whole thing once before you write code.

If you just want the app overview and tech stack, see the main `README.md`. This document is about **working in the repo**.

---

## 1. Repository layout

This is a monorepo with two independent apps and a shared schema package:

```
kalinga/
├── apps/
│   ├── mobile/                    # Flutter app (Dart)
│   └── api/                       # Node.js / Express API
├── packages/
│   └── kalinga_firestore_package/ # Firestore schema, rules, indexes, seed data
└── README.md
```

The Flutter and Node projects are fully independent — each has its own dependency manager and its own build. `cd` into whichever one you're working on. There is no shared build tool; don't try to add one.

The `kalinga_firestore_package` is the **contract**: it defines the Firestore data model, security rules, indexes, and seed data that both apps must conform to. Treat it as the source of truth.

## 2. Prerequisites

Install these once, in this order (each depends on the previous where noted):

1. **Node.js 20+** — https://nodejs.org
2. **Firebase CLI** — `npm install -g firebase-tools` (needs Node)
3. **Flutter SDK** (installs Dart too) — https://docs.flutter.dev/install
4. **Android Studio** — for the Android emulator
5. **Google Cloud CLI** *(optional)* — only needed to enable GCP APIs; you can also do that in the console

Verify everything:
```bash
node --version
firebase --version
flutter doctor      # Android toolchain row should be green
```

> **Windows:** keep the repo and the Flutter SDK OUT of OneDrive and out of paths with spaces (e.g. use `C:\src\kalinga`). OneDrive's file locking breaks Flutter builds. Use PowerShell, not Command Prompt — the commands below assume it.

## 3. First-time setup

### 3.1 Clone

```bash
git clone <repo-url> kalinga
cd kalinga
```

### 3.2 Get added to Firebase

Ask a project owner to add your Google account to the Firebase project **`kalinga-bc97f`** (Firebase Console → Project Settings → Users and permissions → Add member). You need this before the Firebase steps below will work.

Then authenticate:
```bash
firebase login
```

### 3.3 Mobile app

```bash
cd apps/mobile
flutter pub get
flutter run                    # boots on an emulator/device
```

`firebase_options.dart` and the platform config files (`google-services.json`, `GoogleService-Info.plist`) are **committed to the repo** — `git pull` gets you a working config, nothing to generate. (They're not secrets: this is Firebase client config, public by design — see §4.) You do NOT need to run `flutterfire configure` for normal development.

Only re-run it if you're intentionally changing the Firebase project setup (e.g. adding a new platform target):
```bash
dart pub global activate flutterfire_cli
flutterfire configure          # select the EXISTING kalinga-bc97f project — do not create a new one
```
Then commit the regenerated files so everyone picks up the change. Picking the wrong project here (or accidentally creating a new one) is the #1 cause of "invalid/expired token" errors from the API — every token your build mints gets rejected because it's for the wrong Firebase project. If you hit that error, first check:
```bash
grep projectId lib/firebase_options.dart   # every line should say 'kalinga-bc97f'
```

### 3.4 API

```bash
cd apps/api
npm install
cp .env.example .env           # then fill in real values (see below)
npm run dev                    # starts Express with nodemon
```

### 3.5 Schema package (only if you're touching the data model or deploying rules)

```bash
cd packages/kalinga_firestore_package
npm install
npm run validate               # should print "checks": "PASS"
```

## 4. Secrets — the rules

**Never commit secrets.** The `.gitignore` is set up to catch them, but you are the last line of defence. Before every commit, run `git status` and confirm none of these appear:

| File | What it is |
|---|---|
| `serviceAccountKey.json` (any `*-service-account*.json`) | Firebase Admin key — full backend access. **Most dangerous.** |
| `.env` | API keys and config — **the API's `FIREBASE_SERVICE_ACCOUNT` value is the same secret as above**, just pasted into an env var instead of a file. |
| `node_modules/` | Dependencies (regenerated by `npm install`) |

**`google-services.json` / `GoogleService-Info.plist` / `firebase_options.dart` are *not* on this list — they're committed to the repo on purpose.** Firebase client config (apiKey, appId, projectId, …) isn't a secret: it ships inside every built app binary regardless, and Firebase's security model relies on Firestore/Storage Rules, not on hiding this file. Don't add them back to `.gitignore`.

**How secrets are shared:** never over Git, Slack, or email. Use the team's secrets manager / password vault, or generate your own from the Firebase console (Project Settings → Service Accounts → Generate new private key).

If you ever accidentally commit a secret: tell the team immediately, and **rotate the key** (generate a new one) — deleting it from the repo is not enough, because it stays in git history.

## 5. Architecture rules (read before writing data code)

These come from the schema package's `docs/SECURITY_MODEL.md` and `docs/API_BOUNDARIES.md`. They are not optional — the whole security model depends on them.

- **The two apps use different Firebase SDKs.** The mobile app uses the client SDKs (`firebase_auth`, `cloud_firestore`, …) and runs as the logged-in user, subject to Firestore security rules. The API uses the **Admin SDK** (`firebase-admin`), which **bypasses security rules entirely** and runs as a trusted server.

- **All sensitive writes go through the Node API — not straight from the phone.** The client has read-only access to most data via the rules. Anything sensitive (observations, medications, instructions, support requests) is written by the API after it does its own authorization.

- **Because the Admin SDK bypasses rules, the API must authorize every operation itself:** verify the Firebase ID token, check account status, household membership, role/permission, care-recipient assignment, consent/visibility, the private-vs-household boundary, document version, and idempotency — and write an audit event. Don't add an Admin SDK write without these checks.

- **AI never diagnoses.** Kalinga stores structured observations, not autonomous diagnoses. Medication is never inferred from pill appearance alone. OCR output is an unverified draft until a human confirms it. Original caregiver text/audio is preserved separately from any AI output.

- **The schema JSON is the contract.** Use `schema/kalinga-firestore-schema.json` as the source of truth. On the API side, validate against it (e.g. Zod), reject unknown fields on sensitive records, and set `createdAt`/`updatedAt`/ownership/audit fields on the server, never trusting the client for them.

## 6. Deploying rules & indexes

Only deploy from the schema package, and only when you've changed the data model:

```bash
cd packages/kalinga_firestore_package
npm run validate
npm run deploy:firebase
```

Composite indexes take a few minutes to build on Firebase's side — don't run queries that depend on them until the console shows them as ready.

**Known issue:** the `wellbeingCheckIns` composite index is currently rejected by Firestore as redundant (HTTP 400). It's harmless but noisy; it needs cleaning up in `firestore.indexes.json`. Ask before editing the index file — it's part of the shared contract.

## 7. Seeding data

Reference data (government directory, phrasebook, glossary, etc.):
```bash
npm run seed:reference -- --project kalinga-bc97f --dry-run   # preview first
npm run seed:reference -- --project kalinga-bc97f
```

**Demo data is emulator-only.** It uses fictional records and `.example.invalid` emails and must never be imported into the real project:
```bash
npm run emulators
# in another terminal, with FIRESTORE_EMULATOR_HOST set:
npm run seed:demo -- --project kalinga-local
```

## 8. Git workflow

- `main` is the integration branch. Don't commit directly to it — work on a branch and open a PR.
- Branch naming: describe the work, e.g. `feature/voice-log`, `fix/checkin-index`.
- If you change the Firestore schema, update **both** `firestore.rules` and the schema JSON in the **same PR** — they're one contract.
- Before pushing: `git status` and eyeball the staged list for secrets (see section 4).

```bash
git checkout -b feature/your-thing
# ...work...
git add .
git status                     # check for secrets
git commit -m "clear description of the change"
git push -u origin feature/your-thing
```
